Parallel BPE throughput

A byte-level BPE encoder built on snicholls-core's merge and ts-moveables' work-claiming parallel_for. Token for token it gives what tiktoken gives. It is 4.7 to 6.1 times faster than the fastest single-threaded encoder we measured, and with 32 threads it encodes 1.3 to 1.6 GB/s.

"Batch" encodes the 778 files as separate documents across all threads: rayon for the Rust crates, encode_ordinary_batch(num_threads=32) for tiktoken (its best of 8, 16 and 32 threads is shown), batch_encode for rustbpe. "One text" is the whole corpus as one string. Our 32 threads are 31 pool workers plus the calling thread, which parallel_for also puts to work.

Correctness

  • 778 of 778 documents give exactly tiktoken's tokens, for both vocabularies, serially and in parallel, with chunks from 4 KB up to the default size.
  • The whole corpus as one text, cut across the pool, gives exactly its serial tokens. Every document decodes back to its bytes.
  • tiktoken-rs and bpe-openai also match tiktoken on every document, so all the rows above are doing the same work.

Where the speed comes from

  • The split pattern as code. tiktoken spends most of its time in fancy-regex. Here the cl100k and GPT-4 patterns are written out by hand, alternative by alternative, with an ASCII fast path for letter runs. The split runs at 182 MB/s on one thread.
  • Lookups in flight together. The split cuts 32 pieces at a time and hashes and prefetches each one's slot in the vocabulary before looking any of them up. The cache misses on a 4 MB table then overlap instead of queueing.
  • A per-thread piece cache. 93% of pieces are a single token. The other 7% need a merge, and they recur: 195K of them, but only 41K distinct. A 256 KB direct-mapped cache per thread remembers them.
  • Cutting one text safely. A long text is cut at positions the whole-text split is proved to start a piece at: an ASCII letter followed by an ASCII non-letter, or a newline followed by non-whitespace. Workers claim the chunks from a shared cursor, so one text uses every core and still gives its serial tokens. The others parallelise only across documents.
  • The merge. snicholls-core's bpe_encode_piece is tiktoken's byte_pair_merge step for step. It allocates nothing and is constexpr.

Limits of these numbers

  • One corpus, mostly source code. Prose, other languages and other scripts will shift every row; the piece cache helps most where words repeat.
  • One machine. Linux and ARM are still to be measured.
  • Pieces of 1 KB or more take an O(n log n) heap merge with the same tokens. It is about 100 times faster than tiktoken's quadratic merge on a 128 KB piece. Shorter pieces keep the rescanning merge, which is faster at those lengths. bpe-openai is linear in the worst case.
  • The Unicode classes come from the regex module's tables and are checked through tiktoken's tokens on this corpus. Code points assigned in a newer Unicode version than tiktoken's could split differently.
  • Only the cl100k and GPT-4 split patterns are supported. o200k's pattern is not yet supported, and neither are special tokens.
  • The Python rows include building Python lists. The native Rust rows are the fair comparison for the encoders themselves.
